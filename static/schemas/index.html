XML-Schemas für ForgeIEC

Direkt-Download + Dokumentation der XSDs · Stand: 2026-05-21

ForgeIEC arbeitet mit dem PLCopen-XML-Format (tc6_0201) als nativem Projekt-Format. Zusätzlich definiert ForgeIEC eine Reihe von Extensions in eigenen XML-Namespaces, die in PLCopen-konformen <addData>-Containern eingebettet werden.

Diese Seite stellt die zwei dafür benötigten XSD-Schemas zum direkten Download bereit:

1. PLCopen TC6 XML v2.01 (Standard)

Dateitc6_0201.xsd   (~85 KB)
Namespacehttp://www.plcopen.org/xml/tc6_0201
OwnerPLCopen e.V. · Legal terms
Quelleplcopen.org/standards/xml-echange/
VerwendungStrukturelle Validierung von <project>-Wurzelelement und allen Standard-PLCopen-Elementen (POUs, Variablen, Bus-Topologie, Konfiguration).
Lizenz-Hinweis: Die tc6_0201.xsd ist geistiges Eigentum von PLCopen e.V. ForgeIEC bietet diese Datei hier zur einfachen Erreichbarkeit für Werkzeug-Entwickler an, behält aber die unveränderte Original-Struktur (siehe XML-Header-Kommentar in der Datei selbst für Provenance + SHA-256). Bei Fragen zur Re-Distribution: blacksmith@forgeiec.io.

2. ForgeIEC v2 — Extension-Schemas

ForgeIEC schreibt eigene Metadaten in <addData name="https://forgeiec.io/v2/NAME">- Container. Dieses XSD validiert deren Inhalt.

Dateiforgeiec-v2.xsd   (~13 KB)
Namespacehttps://forgeiec.io/v2
LizenzAGPL-3.0-or-later
Element-Coverage
  • <ForgeIecVar> — Variable Security-Flags + Lifecycle-Timestamps
  • <ForgeIecTask> — Per-Task RT-Scheduling + Watchdog-Timeout
  • <busConfig> — Bus-System-Topologie (segment → device → module → setting)
  • <comments> — Free-Text-Comment-Nodes in Variablen-Listen

3. ForgeIEC v2 / sanitize-map (Eigenes Namespace)

Cross-Format-Import-Tool sanitisiert beim Importieren fremder PLCopen-Files (z.B. GX Works3) Identifier, die der IEC 61131-3 Spec nicht entsprechen (Leading-Digit, Sonderzeichen, Reserved-Keywords). Die Rename-Map persistiert die durchgeführten Umbenennungen für einen späteren Roundtrip-Export.

Dateiforgeiec-v2-sanitize-map.xsd   (~4 KB)
Namespacehttps://forgeiec.io/v2/sanitize-map
LizenzAGPL-3.0-or-later
Element-Coverage<renameMap> mit <rename original sanitized reason/>-Children. reason ∈ {leading-digit, invalid-char, reserved-keyword, collision-suffix, empty-name, other}.

Layered Validation

Eine .forge-Datei (oder eine fremde PLCopen-XML) wird in zwei Pässen validiert:

Pass A (Whole-doc):  tc6_0201.xsd  validate  <project>-Tree
                     → strukturelle PLCopen-Korrektheit

Pass B (Extension): pro <addData name="https://forgeiec.io/v2/...">
                     forgeiec-v2.xsd  /  forgeiec-v2-sanitize-map.xsd
                     → ForgeIEC-spezifische Attribute korrekt typisiert

Implementiert in ForgeIEC's FXsdValidator (libxml2 FFI). Spec: PLCopen-IE-1 Sprint-Spec.

Bekannte Non-Konformanz von .forge-Dateien

ForgeIEC's eigenes .forge-Format ist heute noch nicht strikt zu tc6_0201.xsd konform — wir setzen einige Extension- Felder als direkte Attribute auf <pou> / <variable> statt sie in <addData> zu packen:

VerletzungDatei-StellePlan
pouType="anvilVarList"POUsPhase D: Vanilla-Export repackt auf globalVarList + <addData>-Marker
busDirection, deviceIdPer-VariablePhase D: Attribute in <addData>
<returnType>-PositionFunction-POUsPhase D: korrekte XSD-Position
Fehlende <coordinateInfo>HeaderPhase D: leeres Element immer schreiben

Phase D der Sprint-Roadmap adressiert diese systematisch. Vanilla-Export aus ForgeIEC erzeugt sauberes tc6_0201- konformes PLCopen für fremde IDEs (GX Works3, CoDeSys, etc.); intern bleibt die effiziente Direkt-Attribut-Codierung erhalten.
